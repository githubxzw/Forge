# Forge — 统一项目构建与部署管理平台 · 开发方案

> 版本：v0.1（初稿）
> 日期：2026-09-27
> 定位：个人/小团队使用的统一项目管理工具，覆盖 **项目托管 → 构建（前端包/后端包/Docker 镜像/K8s 制品）→ 制品库 → 一键部署 → 回滚** 全链路。

---

## 1. 目标与范围

### 1.1 要解决的问题

| 痛点 | Forge 的解法 |
|---|---|
| 多个项目构建方式各异，命令记不住 | 项目模板 + 统一构建流水线，页面上点一下 |
| 前端包、后端 jar、Docker 镜像、Helm Chart 分散管理 | 统一制品库，带版本、校验和、来源追溯 |
| 部署靠手敲 SSH / kubectl / docker 命令 | 一键部署：选项目 + 选环境 + 选制品 → 执行 → 健康检查 |
| 出问题回滚困难 | 每次部署留档，一键回滚到历史版本 |
| 构建部署过程黑盒 | 实时日志流（WebSocket），全程可观测 |

### 1.2 范围内 / 范围外

**范围内（v1）**
- 项目注册与管理（Git 仓库地址、技术栈识别、构建配置）
- 四类构建产物：前端静态包（dist.tar.gz）、后端包（jar）、Docker 镜像、Helm Chart（K8s 制品）
- 环境管理：SSH 裸机、Docker 主机、K8s 集群
- 一键部署 + 健康检查 + 回滚
- 构建日志实时查看、构建/部署历史

**范围外（v1 不做，留扩展点）**
- 多租户、细粒度 RBAC（先做单管理员 + 简单账号）
- CI 门禁（单测覆盖率、代码扫描）
- 复杂审批流

## 2. 总体架构

### 2.1 形态选型：B/S 架构（Web 控制台 + 服务端）

理由：
1. "一键部署"天然需要 UI 按钮 + 实时日志展示 + 部署历史页面；
2. 浏览器随处可访问，不需要在每台机器装客户端；
3. 同时暴露 REST API，后续想脚本化调用也有入口。

### 2.2 架构图

```
┌─────────────────────────────────────────────────────────┐
│                     forge-web（Vue 3 控制台）             │
│   项目管理 │ 构建流水线 │ 制品库 │ 环境管理 │ 部署/回滚 │ 日志  │
└────────────────────────┬────────────────────────────────┘
                         │ REST + WebSocket
┌────────────────────────▼────────────────────────────────┐
│                    forge-server（核心服务）                │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌─────────────┐  │
│  │ 项目/环境  │ │ 构建编排   │ │ 制品库    │ │ 部署编排/回滚 │  │
│  │ 管理模块   │ │ Pipeline │ │ Registry │ │ Deployer    │  │
│  └──────────┘ └────┬─────┘ └────┬─────┘ └──────┬──────┘  │
│                   │            │               │         │
│  ┌────────────────▼────────────▼───────────────▼──────┐  │
│  │              执行层（Executor，本地线程池起步）          │  │
│  │  Builder SPI: Frontend / Backend / Docker / Helm    │  │
│  │  Deployer SPI: SSH / DockerCompose / K8s(Helm)      │  │
│  └─────────────────────────────────────────────────────┘  │
│        │ SQLite/MySQL        │ 本地制品目录 / MinIO          │
└────────┼─────────────────────┼──────────────────────────────┘
         ▼                     ▼
   ┌──────────┐         ┌─────────────┐      ┌──────────────┐
   │  Git 仓库  │         │ Docker 镜像   │ ──▶ │ 目标环境       │
   │ (拉取代码) │         │ Registry     │      │ SSH/Docker/K8s│
   └──────────┘         └─────────────┘      └──────────────┘
```

**关键决策：单体起步，预留 Agent 扩展。**
v1 由 forge-server 进程内直接执行构建（本地线程池 + 工作目录），不引入分布式执行器。执行层通过 SPI 接口隔离，将来需要"构建机集群"时，把 `Builder/Deployer` 的实现挪到独立的 forge-agent（通过 WebSocket/gRPC 回连 server 领任务）即可，上层编排代码不变。

### 2.3 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 后端 | **Java 17 + Spring Boot 3.x** | 与你现有技术栈一致，维护成本最低；进程管理、SSH（JSch/sshd）、K8s 客户端生态齐全 |
| 前端 | **Vue 3 + TypeScript + Element Plus + Vite** | 管理控制台开发效率高，组件丰富 |
| 数据库 | **SQLite 起步，JPA 抽象可切 MySQL** | 个人工具零运维；表结构稳定后切 MySQL 只改配置 |
| 制品存储 | 文件包：本地磁盘（可切 MinIO）；镜像：Docker Registry（registry:2 或 Harbor） | 简单直接，符合个人规模 |
| K8s 交互 | **Helm（helm upgrade --install）为主**，kubectl 兜底 | Chart 即版本化制品，天然支持 `helm rollback` |
| SSH 执行 | Apache MINA sshd / JSch | 部署到裸机、远程 docker 主机 |
| 实时日志 | WebSocket（STOMP 可不用，裸 WS 即可） | 构建日志流式推送 |
| 认证 | JWT（单管理员起步） | 简单，够用 |

> 备选：Go 单二进制方案（类似 Drone/Gitea，分发极轻），但与你技术栈不符、开发速度慢，不推荐作为主线。

### 2.4 部署 Forge 自身

forge-server 打成 jar（或 Docker 镜像）跑在你的 NAS/服务器/开发机上；数据目录（SQLite + 制品）挂本地卷。forge-web 构建产物由 server 静态托管，最终交付**一个 jar + 一个数据目录**。

## 3. 核心领域模型

```
Project 1──* BuildTask 1──* Artifact *──* Deployment *──1 Environment
   │                                    │
   └── 构建配置(BuildConfig)              └── 部署记录/回滚链
Credential（被 Environment / Registry 引用）
```

### 3.1 实体定义

**Project（项目）**
| 字段 | 说明 |
|---|---|
| name / code | 名称、唯一编码（如 `order-service`） |
| type | `FRONTEND` / `BACKEND` / `FULL`（前后端同仓） |
| repoUrl / defaultBranch | Git 地址与默认分支 |
| stack | 前端：`vue/react`+包管理器；后端：`maven/gradle` |
| buildConfig | JSON：构建命令覆盖、Dockerfile 路径、镜像名、chart 路径等 |
| healthCheck | 部署后健康检查 URL/命令 |

**Environment（环境）**
| 字段 | 说明 |
|---|---|
| name | dev / test / prod … |
| kind | `SSH` / `DOCKER` / `K8S` |
| connConfig | SSH：主机+凭据+部署目录；Docker：主机+compose 模板；K8s：kubeconfig+namespace |
| vars | 环境变量注入（KV，支持占位符替换进配置模板） |

**BuildTask（构建任务）**
| 字段 | 说明 |
|---|---|
| project / branch / commit | 来源 |
| targets | `FRONTEND_TAR` / `BACKEND_JAR` / `IMAGE` / `CHART` 的组合 |
| status | 状态机见 §4.3 |
| logPath | 日志文件（WebSocket 按行重放 + 追加） |
| trigger | `MANUAL` / `WEBHOOK`（v1 先手动） |

**Artifact（制品）**
| 字段 | 说明 |
|---|---|
| type | `TAR` / `JAR` / `IMAGE` / `CHART` |
| version | 策略：`{branch}-{yyyyMMddHHmm}-{commit7}`，如 `main-202609272030-a1b2c3d` |
| ref | 文件路径 / 镜像 tag / chart 包路径 |
| checksum | sha256 |
| buildTaskId | 溯源 |

**Deployment（部署）**
| 字段 | 说明 |
|---|---|
| project / environment / artifact | 部署三元组 |
| status | `RUNNING / SUCCESS / FAILED / ROLLED_BACK` |
| rollbackOf | 回滚指向的 Deployment id |
| result | 健康检查结果、耗时、输出摘要 |

**Credential（凭据）**
- SSH 私钥、kubeconfig、registry 账号、Git token
- **AES-GCM 加密落库**，密钥来自启动配置/环境变量，库被拷走也拿不到明文

### 3.2 关键表（SQL 概要）

```sql
project(id, code, name, type, repo_url, default_branch, stack, build_config_json, health_check_json, created_at, ...)
environment(id, name, kind, conn_config_json, vars_json, created_at, ...)
credential(id, name, kind, cipher_text, iv, created_at)
build_task(id, project_id, branch, commit, targets_json, status, trigger, log_path, started_at, finished_at)
artifact(id, build_task_id, project_id, type, version, ref, checksum, size, created_at)
deployment(id, project_id, env_id, artifact_id, status, rollback_of, result_json, operator, created_at)
```

## 4. 构建能力设计

### 4.1 Builder SPI

```java
public interface Builder {
    BuildTarget supports();                 // FRONTEND_TAR / BACKEND_JAR / IMAGE / CHART
    List<Artifact> build(BuildContext ctx); // 输入：工作目录、项目配置、日志流；输出：制品
}
```

`BuildContext` 携带：项目配置、检出代码目录、版本号生成器、日志消费者（同时写文件 + 推 WebSocket）、环境变量。

### 4.2 四类构建流程

**① 前端包（FRONTEND_TAR）**
```
git checkout → 检测包管理器(package-lock/yarn.lock/pnpm-lock)
→ npm ci --registry=<镜像源> → npm run build
→ dist/ 打包 dist.tar.gz + 生成 sha256 → 制品入库
```
- Node 版本策略：项目可指定（通过 nvm/corepack 管理），默认取构建机版本。

**② 后端包（BACKEND_JAR）**
```
git checkout → ./mvnw -B clean package -DskipTests（或 gradlew bootJar）
→ target/*.jar → 制品入库（记录 jdk 版本）
```

**③ Docker 镜像（IMAGE）**
```
Dockerfile 来源：项目根目录自定义优先，否则用内置模板（按 stack 渲染）
  - 前端模板：多阶段 node build → nginx:alpine 托管 dist
  - 后端模板：多阶段 maven build → eclipse-temurin JRE
→ docker build -t {registry}/{project}:{version}
→ docker push（可配置构建后自动推或手动推）
```
- tag 策略统一用版本号（§3.1 Artifact），保证可追溯；`latest` 由部署时决定是否额外打。

**④ K8s 制品（CHART）**
```
chart 来源：项目自带 chart/ 目录优先，否则用内置通用 Chart 模板
→ 注入 values（image.repo/tag、副本数、环境变量、健康检查）
→ helm package → chart tgz 制品入库
```

### 4.3 任务状态机与并发

```
PENDING → RUNNING → SUCCESS
              └────→ FAILED
RUNNING/SUCCESS ──取消──→ CANCELLED（销毁子进程组）
```
- 执行器：`ThreadPoolExecutor`（可配并行数，默认 CPU 核数）；构建目录按 `{workDir}/{projectId}/{taskId}/` 隔离，任务结束清理（失败保留供排查，可配）。
- 子进程用 `ProcessBuilder` + 进程组，取消时整组 kill，避免残留 node/java 进程。

## 5. 部署能力设计

### 5.1 Deployer SPI

```java
public interface Deployer {
    EnvKind supports();                     // SSH / DOCKER / K8S
    DeployResult deploy(DeployContext ctx); // ctx 含制品、环境、变量、日志流
    DeployResult rollback(DeployContext ctx, Deployment target);
}
```

### 5.2 三类部署策略

**① SSH 裸机**
```
上传制品 → {deployDir}/releases/{version}/ 解压
→ 生成当前配置（env.vars 渲染模板）
→ ln -sfn releases/{version} current   （软链原子切换）
→ 重启服务：systemctl restart {project} 或内置 supervisor 脚本
回滚 = 切回上一个 release 的软链 + 重启
```
- 每环境保留 N 个 release（默认 5），自动清理旧版本。

**② Docker 主机（compose）**
```
渲染 docker-compose.yml 模板（注入 image tag、env）
→ ssh 到目标机执行 docker compose pull && docker compose up -d
→ docker compose ps 等待健康
回滚 = 把 image tag 改回历史版本重新 up
```

**③ K8s（Helm）**
```
helm upgrade --install {release} {chart.tgz}
  -n {namespace} --set image.tag={version} -f env.values.yaml --wait --timeout 5m
回滚 = helm rollback {release} {revision}
健康检查 = 按项目 healthCheck 配置轮询 Ingress/Service URL
```

### 5.3 一键部署交互流（页面）

```
选项目 → 选环境 → 选制品（默认最新√成功） → [预检] → [部署]
预检：连通性（SSH/kubectl）、磁盘、端口占用、镜像存在性
执行：进度步骤条 + 实时日志；结束后自动健康检查并写部署记录
```

## 6. API 设计（REST 概要）

```
POST/GET/PUT/DELETE  /api/projects, /api/environments, /api/credentials
POST   /api/builds                    # 发起构建 {projectId, branch, targets[]}
GET    /api/builds/{id}               # 状态 + 元信息
GET    /ws/logs/builds/{id}           # 构建日志流（重放+追加）
GET    /api/artifacts?projectId=&type=
POST   /api/artifacts/{id}/push       # 镜像推送到 registry
POST   /api/deployments               # 一键部署 {projectId, envId, artifactId}
POST   /api/deployments/{id}/rollback
GET    /ws/logs/deployments/{id}
GET    /api/projects/{id}/deploy-history?envId=
```

统一返回 `{code, message, data}`；错误码分段（参数/凭据/构建/部署/环境连通）。

## 8. 安全设计

1. **凭据加密**：AES-256-GCM，密钥来自 `FORGE_SECRET_KEY` 环境变量（首次启动自动生成并打印）；库文件泄露不等于凭据泄露。
2. **认证**：v1 单管理员，登录发 JWT（有效期可配）；后续可扩多用户 + 角色（谁可以点"部署到 prod"）。
3. **审计**：deployment 表记录 operator + 来源 IP；页面可见"谁在什么时候部署了什么"。
4. **命令注入防护**：所有 shell 命令用参数化数组（`ProcessBuilder(List<String>)`），禁止字符串拼接用户输入。
5. **制品完整性**：文件制品入库即算 sha256，部署前校验。

## 9. 里程碑计划

| 阶段 | 周期 | 交付内容 | 验收标准 |
|---|---|---|---|
| **M1 骨架 + 后端链路** | 1~2 周 | 工程搭建（forge-server/forge-web）、项目/环境 CRUD、凭据加密存储、**后端 Maven 构建 → jar 制品 → SSH 软链部署 → 回滚**、WebSocket 日志 | 一个真实 Spring Boot 项目能在页面上完成构建+部署+回滚，全程日志可见 |
| **M2 前端 + Docker** | 1~2 周 | 前端构建（npm→tar）、内置 Dockerfile 模板、**镜像构建/推送**、Docker 主机 compose 部署 | 前后端项目均可打出镜像并部署到 docker 主机 |
| **M3 K8s + 体验完善** | 1~2 周 | 内置 Helm Chart 模板、**K8s 部署/回滚/健康检查**、部署预检、制品库页面完善 | 一键部署到 K8s 并自动健康检查，失败可一键回滚 |
| **M4 效率增强** | 按需 | Git Webhook 自动构建、构建缓存（maven/npm）、通知（钉钉/飞书 webhook）、多用户 | 提交即构建，构建结果自动通知 |

> 建议严格按 M1→M2 串行，**每个里程碑都以"真实项目跑通"为验收**，避免先铺大而全的框架。

## 11. 关键风险与对策

| 风险 | 对策 |
|---|---|
| 构建环境依赖（node/jdk/maven/docker/helm 版本） | v1 约定"构建机自带工具链"，Forge 只做探测与版本显示；M4 再考虑工具链容器化（docker-in-docker 或每类构建器一个构建镜像） |
| 长任务进程管理（僵尸进程、取消不干净） | 进程组 kill + 任务结束钩子清理工作目录 + 超时上限 |
| K8s 各家集群差异（kubeconfig 权限、CRD） | 只依赖标准 Helm/K8s 原语，不做厂商绑定；kubeconfig 可按环境传入 |
| SQLite 并发写 | 构建高频写的是日志文件而非 DB，DB 只写状态变更，压力极小 |
| 制品膨胀 | 按项目配置保留策略（保留最近 N 个 + 被部署引用的不清理） |

## 12. 待确认决策点

1. **技术栈**：推荐 Spring Boot 3 + Vue 3（贴合现有技能）；若更想要"单文件分发"可改 Go。
2. **部署目标优先级**：M1 先打通哪类环境？（方案默认 SSH，若你主力是 K8s 可把 K8s 提到 M1）
3. **镜像仓库**：自建 registry:2 / Harbor，还是用现有云厂商仓库？
4. **Forge 自身运行位置**：Mac 本机 / 家里服务器 / NAS？
